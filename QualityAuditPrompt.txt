You are an AI coding assistant auditing documentation that LeanDoc has
already generated for a Lean/Lake project. The user has pasted you this
file after running `lake exe leandoc` (directly, or via
`InstallationPrompt.txt`'s install flow). Your job is to sanity-check
the *result*, not to trust it blindly just because the tool ran without
error — LeanDoc can produce output that's technically valid and still
low-quality, stale, or misconfigured.

This is a **manual audit, inherently a stopgap** — a real CI-enforced
freshness gate is what `InstallationPrompt.txt`'s optional CI/pre-commit
templates are for (task T20/T34); this prompt is for a one-off or
periodic check, not a substitute for that. Never hand-edit generated
output to "fix" a finding — point at the Lean source, `leandoc.toml`,
or (if it looks like a genuine LeanDoc bug) LeanDoc's own issue tracker
instead.

STATUS NOTE (remove once LeanDoc has a first tagged release): several
checks below reference behavior that's real and tested as of this
writing (2026-09-23) but from an interface that isn't frozen yet — if a
check below doesn't match what you actually find, say so plainly and
adapt rather than forcing the project's output to match a stale
description.

1. Confirm there's something to audit
   - Find `leandoc.toml` (or confirm its defaults apply) and the
     `docs_dir` it points at (default `docs/`). If `docs_dir` doesn't
     exist or is empty, stop and tell the user to run `lake exe
     leandoc` first — there's nothing to audit yet.

2. Read `leandoc.toml`'s configuration before judging anything against
   it — don't assume defaults, and don't assume every flag exists
   - `[modules] exclude` — don't flag an excluded module's absence as
     a coverage gap; it was deliberately left out.
   - `[renderer] jekyll` — determines which checks in step 8 apply.
   - `[compliance]` (task T41) — if `enabled = true`, treat its
     `author`/`license` as the standard to check file headers against
     in step 4 (LeanDoc's own `checkComplianceHeader` already warns on
     this when the project's `lake exe leandoc` runs — cross-check
     that those warnings were actually addressed, not just emitted and
     ignored). **If `leandoc.toml` doesn't exist, or has no
     `[compliance]` section:** don't silently assume either "fully
     compliant" or "no compliance checks wanted" — propose sensible
     default values to the user (e.g. off, matching LeanDoc's own
     default) and ask whether they want compliance checking as part of
     this audit before proceeding with that section.
   - Naming-conventions and docstring-"plain English quality" flags
     are designed but **not built yet** (`wip/todo.md` tasks T41/T42)
     — don't check for them, and don't tell the user they exist.

3. Freshness
   - Regenerate (`lake exe leandoc`, plus `lake exe leandoc <path>` for
     any other configured projects) and diff against what's committed,
     the same way the optional CI/pre-commit templates do — check
     `docs_dir/reference`, `docs_dir/toc.md`, and `docs_dir/index.md`
     (only the `<!-- leandoc:nav:start -->`/`<!-- leandoc:nav:end -->`
     region of the latter should ever change; if more of it changed,
     something wrote to it that shouldn't have).
   - Also applies *within* a docstring: if it shows a code example,
     does that example still reflect the current API, or has the
     signature moved on without the example being updated? This needs
     actually reading docstring content, not just re-running the tool.

4. Docstring coverage and quality
   - Not just presence — does each docstring give a plain-language
     summary, or is it a one-liner restating the signature? Mathlib's
     own standard is a good bar to cite directly rather than inventing
     new phrasing for the same idea: "doc strings should convey the
     mathematical meaning of the definition... allowed to lie slightly
     about the actual implementation"
     (leanprover-community.github.io/contribute/doc.html). Report
     specific gaps (declaration + module), not just a count.
   - If `[compliance]` is enabled (step 2), also check the file-header
     requirement was actually satisfied, not just that LeanDoc's own
     warning was seen and ignored.
   - If the project depends on Batteries or Mathlib, its own `#lint`
     command (`docBlame`/`docBlameThm` — Batteries; `tacticDocs` —
     Mathlib only) is a real, complementary presence-only check worth
     recommending the user also run — LeanDoc's renderer already
     performs the equivalent check itself (an undocumented declaration
     renders as `*(not documented)*`, plainly visible on its page), so
     this is a second opinion, not something this audit needs to
     reimplement.

5. Generated-declaration noise
   - Spot-check that Lean's own scaffolding (`.rec`, `.casesOn`,
     `.noConfusion`, equation lemmas, `_sizeOf_*`, ...) isn't leaking
     into rendered pages — a real LeanDoc bug if found, not a nitpick
     (see `wip/todo.md` task T7). Also worth checking, since it was
     found but not yet fixed as of this writing (task T42): instances,
     Prop-projection `def`s, and `parenthesizer`/`formatter`/
     `delaborator`-suffixed auxiliary declarations currently *do* still
     show up (LeanDoc's noise filter doesn't exempt them the way
     Batteries' own linters do) — don't report these as a *bug* unless
     `wip/todo.md` task T41's exemption-logic improvement has since
     landed; check its status before flagging this as new.

6. Structure and navigation
   - `docs_dir/index.md` should exist and link to `reference/modules.md`
     and `toc.md` (task T18 — check the nav block, not just that the
     files individually exist).
   - `docs_dir/reference/` holds one page per module plus
     `modules.md`; `docs_dir/toc.md` groups every documented
     declaration by kind (Definitions / Theorems & Axioms /
     Structures & Inductives / Other). If a project has enough
     declarations that a flat list stops being navigable, `toc.md` is
     what should be serving as the basic index — confirm it's
     reasonably organized, not just present.
   - Confirm the generated declaration reference isn't presented as if
     it were a curated public API — it isn't (task T25): it's every
     included declaration, minus noise filtering. If a project's guide
     content implies otherwise, that's worth flagging.

7. Narrative vs. raw reference dump
   - Does the site have *any* conceptual/connective content (a
     hand-written `index.md` intro, a `manual.md`-equivalent, a guide
     page), or is it 100% auto-generated declaration listing with
     nothing explaining how the pieces fit together? Does the landing
     page actively route a first-time reader toward guide content
     before they hit a wall of possibly-undocumented declarations?

8. GitHub Pages / Jekyll compatibility (only if `[renderer] jekyll =
   true`, the default — skip this section entirely if `false`)
   - Every generated page's front matter must include `layout:
     default` (task T29) — front matter alone isn't enough for Jekyll
     to actually apply LeanDoc's stylesheet to a page; confirmed
     against Jekyll's own documented behavior, not assumed. Spot-check
     a few generated pages, not just one.
   - `docs_dir/assets/style.css` and `docs_dir/_layouts/default.html`
     should exist (LeanDoc writes both once, task T29 — vendored from
     doc-gen4, matching what Mathlib/cslib actually look like). If the
     project intentionally customized either after the first
     generation, don't flag the customization itself as a problem —
     confirm it's still valid CSS/a valid Jekyll layout, nothing more.
   - Internal links use Jekyll's `{% link %}` tag, which is supposed
     to fail the *actual* Jekyll build if a target doesn't exist —
     this audit can't run a real Jekyll build to verify that (no local
     Jekyll toolchain is assumed to be available), so treat this as an
     honest gap: recommend the user confirm via an actual GitHub Pages
     deploy if this matters to them, don't claim to have verified it.
   - Do relative links still work when served from `/docs` on `main`
     (GitHub Pages' typical setup)? Spot-check, don't assume.

9. Rendering correctness
   - Spot-check for broken Markdown (unclosed code fences, malformed
     tables) in a sample of generated pages, especially ones with
     unusual docstring content (embedded code blocks, special
     characters in declaration names).

10. Known, currently-unrendered gaps — note these rather than treat
    them as failures, since there's nothing in current output to check
    against yet:
    - **Source links**: `DeclMeta.range` (task T7) captures each
      declaration's source location, but nothing in the renderer
      surfaces it as a link back to source today. Not a bug to report
      here — a known, tracked limitation.
    - **Version stamping**: generated output doesn't record which Lean
      toolchain it was built against. Same treatment.

11. Report findings by category (using the numbered sections above),
    most actionable first. Distinguish clearly between:
    - A LeanDoc bug (noise leaking through, a broken link LeanDoc
      itself generated)
    - A project-side gap (missing docstrings, no guide content, a
      missing compliance header)
    - A known, already-tracked limitation (section 10) — mention for
      completeness, don't present as new
