You are an AI coding assistant helping a developer add LeanDoc (a
documentation generator for Lean 4 projects) to their existing Lean/Lake
project. The user has pasted you this file as their installation prompt.
Follow these steps, adapting paths/names to what you find in their repo.

This installs LeanDoc as a *user* of it — do not set up anything from
LeanDoc's own *development* tooling (its `test/` suite, its
`.githooks/pre-commit` test-on-commit hook, `git config core.hooksPath
.githooks`, or similar). None of that belongs in a project that merely
depends on LeanDoc; it's specific to working on LeanDoc's own source.
See "Users vs. developers of LeanDoc" in LeanDoc's own `README.md` if
this distinction matters for a step below. None of LeanDoc's own
`lean_exe` targets are named anything a project would plausibly also
want for itself (`leandoc`, `leandoc-test` — task T36 renamed the
latter from the generic `test` specifically to avoid this), so running
your *own* `lake exe <name>` commands after installing LeanDoc as a
dependency won't accidentally resolve to one of LeanDoc's instead.

1. Confirm this is a Lean/Lake project
   - Look for `lakefile.lean` or `lakefile.toml` and `lean-toolchain` at
     the repo root. If neither exists, stop and tell the user this isn't
     a Lake project yet (LeanDoc extracts docs from an elaborated Lake
     build, so it needs one).

2. Review installation parameters with the user before writing anything
   - Do not silently apply defaults. Present each parameter below,
     explain in a sentence what it controls, state the recommended
     default, and ask the user to confirm it or give an override. Use
     their answers in every later step instead of the defaults.

     a. **Dependency version.** Which LeanDoc revision to pin in the
        `require` line — a tag once releases exist, otherwise a branch
        or commit. *Recommended default:* the latest tagged release; if
        none exists yet, `main` (and flag that this is less stable than
        pinning a tag, since `main` can change under them).
     b. **Intermediate JSON directory (`json_dir`).** Where per-module
        `metadata.json` build artifacts are written — regenerated every
        run, gitignored, never meant to be read directly.
        *Recommended default:* `.leandoc/`.
     c. **Rendered docs directory (`docs_dir`).** Where the final
        generated documentation is written. *Recommended default:*
        `docs/`, since GitHub Pages can serve that directly from `main`
        with zero extra config.
     d. **Commit rendered docs to git?** Whether `docs_dir` is tracked
        or gitignored. *Recommended default:* commit it (matches the
        zero-config GitHub Pages story above). The alternative is
        treating it as a pure CI/CD build artifact, published by a
        separate workflow instead — only pick that if the user already
        has (or wants) such a pipeline.
     e. **Included/excluded modules.** *Recommended default:* leave
        `include` empty — LeanDoc scans the project's own
        `lakefile.toml` (its `lean_lib`/`lean_exe` targets) and
        documents everything it finds (task T21, done 2026-09-21).
        Only ask the user to name modules explicitly in `include` if
        they want a subset rather than the whole package. Only
        understands `lakefile.toml`, not the `lakefile.lean` DSL — a
        project using the latter still needs an explicit `include`
        list. Ask about `exclude` (dotted module names, e.g.
        `"Foo.Bar"`) if there are internal modules to leave out either
        way.
     f. **Jekyll-targeted output (`[renderer] jekyll`).** Whether
        generated pages carry Jekyll front matter, use Jekyll's
        `{% link %}` tag for internal links, and get a written
        `_config.yml` (task T22/T28/T31) — vs. plain, portable Markdown
        with ordinary relative links and no Jekyll-specific content.
        *Recommended default:* `true` (the LeanDoc default) whenever
        `docs_dir` will be published via GitHub Pages from step 2c/2d's
        defaults, since GitHub Pages runs Jekyll on `docs_dir` unless
        told not to — `false` output left in that setup would be served
        unprocessed (raw Markdown source, not a readable page). Set to
        `false` only if the user has explicitly said they don't want
        GitHub Pages/Jekyll for these docs (browsing in an IDE, serving
        from elsewhere, or an existing Jekyll setup they don't want
        LeanDoc's `_config.yml`/`{% link %}` output mixed into — see
        step 4's note on existing `docs_dir` content either way).

3. Add LeanDoc as a Lake dependency
   - In `lakefile.lean` / `lakefile.toml`, add a `require` entry for the
     `LeanDoc` package, pinned to the version confirmed in step 2a:

       [[require]]
       name = "LeanDoc"
       git = "https://github.com/JVerstry/LeanDoc"
       rev = "<step 2a value>"

     (TODO: confirm this once LeanDoc has a tagged release — the
     package name and repo URL are fixed now that `lakefile.toml`
     exists, but no release has been cut yet, so `rev` still has to be
     a branch/commit rather than a tag today.)
   - Run `lake update` to fetch it.

4. Ensure the `docs_dir` from step 2c exists at the repo root
   - Check whether it already exists. If it doesn't, create it.
   - Don't worry about populating it with real content yet — that
     happens in step 6 (initial generation). This step just guarantees
     the directory exists so the repo's Pages settings can be pointed at
     `main` / that directory immediately. If step 2f's answer was
     `jekyll = true` (the default), no `.nojekyll` marker is needed:
     LeanDoc's renderer emits Jekyll-ready output itself — front matter
     with `layout: default` on every generated page, its own vendored
     stylesheet (`docs_dir/assets/style.css`, task T29 — matches the
     Lean ecosystem's own look, sourced from doc-gen4) and layout
     (`docs_dir/_layouts/default.html`), internal links via Jekyll's
     `{% link %}` tag (task T22/T28) — so GitHub Pages' default Jekyll
     processing turns the generated Markdown into a styled site
     without a GitHub Pages `theme:`/`remote_theme:` dependency at
     all. Both the stylesheet and layout are written once and never
     overwritten — free to edit either directly afterward.
   - **If `docs_dir` already has hand-written Markdown pages in it**
     (e.g. an existing landing page) and step 2f's answer is
     `jekyll = true`: LeanDoc's renderer only adds front matter to the
     pages *it* generates (under `docs_dir/reference/`, plus
     `docs_dir/toc.md`), never to existing hand-written ones — task
     T31. One exception, task T18: `docs_dir/index.md` specifically —
     if it doesn't exist yet, LeanDoc creates it itself (with front
     matter already included), so no manual step is needed for it. If
     it *does* already exist, LeanDoc still never touches its front
     matter (same as any other pre-existing page) — it only ever
     rewrites the region between
     `<!-- leandoc:nav:start -->`/`<!-- leandoc:nav:end -->` markers,
     if those are present. Check any *other* pre-existing `.md` files
     directly under `docs_dir` (and `docs_dir/index.md` if it already
     existed) and, if Jekyll processing is wanted site-wide, add a
     front-matter block with `layout: default`
     (`---\nlayout: default\n---\n`) to each one that's missing it —
     not just an empty `---\n---\n` block, since (task T29) a layout is
     what actually makes LeanDoc's stylesheet apply to that page, not
     front matter alone; otherwise those pages stay unprocessed
     "static files" (or processed but unstyled) sitting next to
     properly-styled generated ones — an inconsistent, partly-broken
     site. Tell the user what was changed rather than doing this
     silently. If `jekyll = false` was chosen instead, skip this —
     nothing in `docs_dir` should have Jekyll-specific content.

     [renderer]

                         # there's no real choice to make here yet
     jekyll = <step 2f value, default true>   # front matter, {% link %}
                         # links, and a written _config.yml (task
                         # T22/T28/T31) vs. plain portable Markdown

   `include`/`exclude` entries are dotted Lean module names (e.g.
   `"Foo.Bar"`). Leaving `include` empty is now the recommended default
   (task T21, done) — LeanDoc scans the project's `lakefile.toml` for

6. Update `.gitignore`
   - If the repo has no `.gitignore` yet, create one.
   - Before appending anything, check whether `json_dir` (and, if
     relevant, `docs_dir`) is already covered by an existing pattern
     (an exact match, or a broader one like `.lean*` or a catch-all) —

   - Add the `json_dir` from step 2b so intermediate metadata never

   - Only add `docs_dir` to `.gitignore` if the user chose "gitignored"

7. Run the initial generation: `lake exe leandoc` — run from the
   **target project's own root** (not from a separate LeanDoc checkout).
   Once step 3's `require` + `lake update` pulled LeanDoc in as a
   dependency, `lake exe` resolves executables from dependencies the
   same way it resolves the current package's own ones — the same
   pattern Mathlib uses for `lake exe cache get` in a project that
   depends on Mathlib, run from that project's own root, not Mathlib's.
   No path argument is needed: the executable's project-path argument
   (task T13) defaults to `.`, which is exactly the target project,
   since that's the directory `lake exe` runs it from. (The explicit
   `lake exe leandoc <path>` form exists for LeanDoc's own development
   — e.g. pointing at its `demo/` test fixture from within its own
   repo — not for a normal install.)

8. Report back to the user
   - Show what was added/changed (dependency line, `leandoc.toml`,
     `.gitignore` diff), and restate the parameter choices from step 2
     so they have a record of what was decided.
   - Point them at where the generated docs landed (`docs_dir`).
   - Do not commit anything on their behalf without asking first.
   - **Mention, but do not set up, a CI drift-check** (task T20): CI
     that regenerates docs on every push/PR and fails if the result
     doesn't match what's committed — catching "docs committed but not
     regenerated after a source change" the same way LeanDoc's own CI
     does for its own repo. This is deliberately **not** an automatic
     part of this install flow, for one concrete reason: the `require`
     line from step 3 still pins a branch, not a tagged release (no
     release exists yet — see the STATUS NOTE at the top of this file),
     so a generated CI workflow would silently pick up LeanDoc's own
     breaking changes on every run. Only write the workflow below if
     the user explicitly asks for it (and flag that caveat when they
     do, so it's an informed choice, not a surprise later):

     ```yaml
     name: Docs freshness
     on:
       push:
         branches: [main]
       pull_request:
         branches: [main]
     jobs:
       check:
         runs-on: ubuntu-latest
         steps:
           - uses: actions/checkout@v4
           - name: Install elan
             run: |
               curl https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh -sSf | sh -s -- -y --default-toolchain none
               echo "$HOME/.elan/bin" >> "$GITHUB_PATH"
           - name: Cache Lake build artifacts
             uses: actions/cache@v4
             with:
               path: .lake
               key: lake-${{ runner.os }}-${{ hashFiles('lean-toolchain', 'lakefile.toml', 'lake-manifest.json') }}
           - run: lake build
           - run: lake exe leandoc
           - name: Check generated docs are committed and up to date
             run: |
               PATHS="<docs_dir>/reference <docs_dir>/toc.md <docs_dir>/index.md"
               if [ -n "$(git status --porcelain -- $PATHS)" ]; then
                 echo "::error::Generated docs are out of date or uncommitted." >&2
                 echo "Run 'lake exe leandoc' locally, then commit the result." >&2
                 git status --porcelain -- $PATHS
                 exit 1
               fi
     ```

     Substitute the real `docs_dir` (step 2c's value) for `<docs_dir>`.
     Gates `<docs_dir>/reference` and `<docs_dir>/toc.md` (fully
     generated, task T18) plus `<docs_dir>/index.md` (task T18: only
     partially generated — LeanDoc only ever touches the
     `<!-- leandoc:nav:start -->`/`<!-- leandoc:nav:end -->`-delimited
     region inside it, so this only flags real drift there, never a
     hand-written page with no such markers, since LeanDoc never
     changes those at all). Deliberately doesn't gate all of `docs_dir`
     — a project may have other hand-written pages alongside it that CI
     shouldn't fail on. Fails the build
     rather than auto-committing the regenerated docs: consistent with
     "do not commit on the user's behalf without asking," above — an
     auto-committing CI job is a bigger trust step this file doesn't
     take unless asked to.
   - **Mention, but do not set up, a local pre-commit freshness check**
     (task T34) — the same drift concern as the CI drift-check above,
     just enforced locally before a commit lands instead of after a
     push. Even more clearly opt-in than the CI version: `lake exe
     leandoc` does a full elaboration, which can be genuinely slow on a
     large project (see this file's `README.md` note on docstring-edit
     rebuild cost, and consider recommending
     [LeanPerformance](https://github.com/JVerstry/LeanPerformance) if
     the user is worried about this) — running it before *every*
     commit is a real, ongoing cost, not a one-time setup cost, unlike
     LeanDoc's own `.githooks/pre-commit` (which only runs the fast
     `lake exe leandoc-test`). Only set this up if the user explicitly
     asks, and make sure they understand it's a per-commit elaboration
     cost before they opt in:

     ```sh
     #!/bin/sh
     set -e
     echo "Checking generated docs are up to date..."
     lake exe leandoc
     PATHS="<docs_dir>/reference <docs_dir>/toc.md <docs_dir>/index.md"
     if [ -n "$(git status --porcelain -- $PATHS)" ]; then
       echo "Generated docs are out of date - committing the regenerated result too." >&2
       git status --porcelain -- $PATHS
       exit 1
     fi
     ```

     Substitute `<docs_dir>` as above. Ship it as a tracked file (e.g.
     `.githooks/pre-commit`, mirroring LeanDoc's own convention) with
     opt-in activation via `git config core.hooksPath .githooks`, not
     installed into `.git/hooks/` directly (never committed, so a
     fresh clone wouldn't have it) and not made automatic — the user
     has to run that `git config` line themselves, same as LeanDoc's
     own developers do.
