You are an AI coding assistant helping a developer add LeanDoc (a
documentation generator for Lean 4 projects) to their existing Lean/Lake
project. The user has pasted you this file as their installation prompt.
Follow these steps, adapting paths/names to what you find in their repo.

STATUS NOTE (remove once LeanDoc has a first release): LeanDoc itself is
still pre-implementation. Some steps below reference an executable name,
CLI flags, and a Lake dependency line that don't exist yet — treat those
as placeholders to fill in once LeanDoc ships, not as verified commands.

1. Confirm this is a Lean/Lake project
   - Look for `lakefile.lean` or `lakefile.toml` and `lean-toolchain` at
     the repo root. If neither exists, stop and tell the user this isn't
     a Lake project yet (LeanDoc extracts docs from an elaborated Lake
     build, so it needs one).

2. Review installation parameters with the user before writing anything
   - Do not silently apply defaults. Present each parameter below,
     explain in a sentence what it controls, state the recommended
     default, and ask the user to confirm it or give an override. Use
     their answers in every later step instead of the defaults.

     a. **Dependency version.** Which LeanDoc revision to pin in the
        `require` line — a tag once releases exist, otherwise a branch
        or commit. *Recommended default:* the latest tagged release; if
        none exists yet, `main` (and flag that this is less stable than
        pinning a tag, since `main` can change under them).
     b. **Intermediate JSON directory (`json_dir`).** Where per-module
        `metadata.json` build artifacts are written — regenerated every
        run, gitignored, never meant to be read directly.
        *Recommended default:* `.leandoc/`.
     c. **Rendered docs directory (`docs_dir`).** Where the final
        generated documentation is written. *Recommended default:*
        `docs/`, since GitHub Pages can serve that directly from `main`
        with zero extra config.
     d. **Commit rendered docs to git?** Whether `docs_dir` is tracked
        or gitignored. *Recommended default:* commit it (matches the
        zero-config GitHub Pages story above). The alternative is
        treating it as a pure CI/CD build artifact, published by a
        separate workflow instead — only pick that if the user already
        has (or wants) such a pipeline.
     e. **Jekyll.** Whether the user plans to let GitHub Pages run
        Jekyll over `docs_dir` (e.g. because they want Jekyll includes,
        layouts, or a Jekyll theme). *Recommended default:* no — most
        projects don't want Jekyll post-processing their generated
        docs, since Jekyll ignores/rewrites underscore-prefixed
        files/folders and applies its own theme to Markdown. Default to
        adding a `docs_dir/.nojekyll` marker unless the user says they
        do want Jekyll, in which case skip it.
     f. **Included/excluded modules.** Which modules LeanDoc documents,
        as dotted module names (e.g. `"Foo.Bar"`), one per entry.
        *Current limitation:* whole-package scanning doesn't exist yet
        (T9) — you must ask the user to name every top-level module
        they want documented; there's no "everything" default today.
        Ask separately if there are internal modules to exclude once
        whole-package scanning lands.

3. Add LeanDoc as a Lake dependency
   - In `lakefile.lean` / `lakefile.toml`, add a `require` entry for the
     `LeanDoc` package, pinned to the version confirmed in step 2a:

       [[require]]
       name = "LeanDoc"
       git = "https://github.com/JVerstry/LeanDoc"
       rev = "<step 2a value>"

     (TODO: confirm this once LeanDoc has a tagged release — the
     package name and repo URL are fixed now that `lakefile.toml`
     exists, but no release has been cut yet, so `rev` still has to be
     a branch/commit rather than a tag today.)
   - Run `lake update` to fetch it.

4. Ensure the `docs_dir` from step 2c exists at the repo root
   - Check whether it already exists. If it doesn't, create it.
   - If step 2e's answer was "no Jekyll" (the default), add an empty
     `docs_dir/.nojekyll` marker file if one isn't already there. Skip
     this if the user said they do want Jekyll.
   - Don't worry about populating it with real content yet — that
     happens in step 6 (initial generation). This step just guarantees
     the directory (and its GitHub Pages marker, if applicable) exists
     so the repo's Pages settings can be pointed at `main` / that
     directory immediately.

5. Create a `leandoc.toml` config file at the repo root, sibling to
   `lakefile.toml`, using the values confirmed in step 2. This schema
   is now real (task T8) — parsed with Lake's own TOML
   parser/decoder (`Lake.Toml`) and exercised end-to-end against
   LeanDoc's own `demo/` project, not a guess:

     [output]
     json_dir = "<step 2b value, default .leandoc/>"
     docs_dir = "<step 2c value, default docs/>"

     [modules]
     include = ["<step 2f value>"]
     # exclude = [...]   # only if the user named exclusions in step 2f

     [renderer]
     name = "markdown"   # reserved for T9 — no renderer exists yet,
                         # so this field is parsed but currently unused

   `include`/`exclude` entries are dotted Lean module names (e.g.
   `"Foo.Bar"`), one per module — **not** yet "the whole package" by
   default. Whole-package scanning (so `include` can be omitted
   entirely) is T9 work; today, an empty or missing `include` list
   means the extractor has nothing to do. Ask the user which modules
   they want documented if this comes up during install.

6. Update `.gitignore`
   - If the repo has no `.gitignore` yet, create one.
   - Before appending anything, check whether `json_dir` (and, if
     relevant, `docs_dir`) is already covered by an existing pattern
     (an exact match, or a broader one like `.lean*` or a catch-all) —
     don't add a duplicate or redundant entry.
   - Add the `json_dir` from step 2b so intermediate metadata never
     gets committed — it's regenerated on every run, same treatment as
     `.lake/`.
   - Only add `docs_dir` to `.gitignore` if the user chose "gitignored"
     in step 2d. Otherwise leave it tracked.

   - Show what was added/changed (dependency line, `leandoc.toml`,
